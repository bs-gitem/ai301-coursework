## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (OS, the project's version or commit, and any runtime the issue's own bug-report template asks for, e.g. driver, shell, build profile, Python/Node version), read against the issue's stated target in the issue context and the repo-facts template line. | The record names the operating system AND the project version/commit that was run; if the repo's template asks for another field that the issue's behavior depends on (driver, shell, build profile), that field is present too. A report with no environment record fails, however good the artifact is. | required |
| steps-followable | The reproduction steps in the repro report, read from the starting state to the trigger. | Every step is a concrete command, input, or action a stranger could copy on the recorded environment, and the steps reach the trigger the issue names without relying on a private repo, an unshared config, or "my setup". A step that says only "trigger the bug" or omits the input that causes it fails. | required |
| evidence-present | The artifacts in the repro report: output excerpts, logs, error text, screenshots, measurements, produced by the author's own run. | At least one artifact from the author's own run is shown verbatim (not described). Statements such as "I verified", "confirmed", "guaranteed reproducible", or a root-cause diagnosis with no artifact behind them fail. A me-too with no artifact fails. | required |
| behavior-matches-issue | The artifact read against the issue's described behavior (the exact error, exit code, crash, missing header, visible symptom), AND the input/command used read against the issue's trigger (its syntax, flag, file, or sequence). | First read the report's own conclusion. If it claims the bug reproduced: the artifact shows the same behavior the issue describes, produced by the same trigger the issue describes; a different error (a graceful validation error where the issue reports a crash; a compile error where the issue reports a runtime error), a different symptom, or an input that is not the issue's trigger fails, no matter how confident the narration. If it claims it could NOT reproduce: this check passes when the artifact shows the issue's own trigger being run (same command, input, or sequence) and the actual outcome, even though that outcome is the normal one; the honesty of that conclusion is judged by honest-outcome, not here. An artifact from a trigger that is not the issue's fails in both cases. | required |
| honest-outcome | The report's stated conclusion (reproduced / could not reproduce / partially) read against what its own artifacts and environment show, and against the issue's target version or platform. | The stated conclusion equals what the artifacts show. A cannot-reproduce that shows the attempt, records the environment, and names what differed from the issue passes. A report that reproduces on a version or platform different from the issue's stated target passes only if it says so and explains why it still applies; a silent deviation fails. A conclusion that claims more than its artifacts show fails. | required |
| claim-specific | The claim comment read against the issue context. | The claim names the issue's specific symptom or trigger in the author's own words and states what the author will do next (reproduce, investigate) without asserting a fix, a deadline, or a guarantee; "+1", "same here", "assign me", or text that could be pasted on any issue fails. | required |
| conventions-met | The repo-facts block (bug-report template asks, contribution policy, stated AI policy) read against both comments. | Disclosure is required ONLY when the repo-facts policy line says AI use must be disclosed (words such as "must disclose", "all AI usage must be disclosed", "state the tool used"); then a comment that does not disclose fails (course packages are AI-assisted by definition). A policy that only restricts AI-generated text, asks for a human in the loop, or asks that comments be written in the author's own words is satisfied by a comment that is specific to this issue and reads as the author's own account; it does not require a disclosure sentence. No AI policy, or a permissive one, imposes nothing. Separately, if the bug-report template asks for a field the report needs to be actionable (logs, version, OS), that field is supplied. | required |
| control-run | The repro report, looking for a second run that isolates the variable (a control input, the previous version, the expected path; for a cannot-reproduce, a second attempt with one difference changed). | A second run is shown and its output is contrasted with the first. | preferred |

## Verdict rule

accept if every `required` check passes. Any `required` check graded `fail` or `unclear` makes the verdict `reject` (unclear counts as fail: proof I cannot verify is proof that is not ready to post). `preferred` checks never change the verdict; they appear in the summary only. In live claim-only mode, env-recorded, steps-followable, evidence-present, behavior-matches-issue, honest-outcome and control-run are reported `unclear` with evidence `not yet applicable: claim-only draft` and are left out of the rule; the verdict then rests on claim-specific and conventions-met alone.
