## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-grounded | The plan's stated cause (its diagnosis or "what I found" sentence) read against the repro-evidence block: every numbered step, every artifact, and especially every control run (a second run with one variable changed) and the Expected/Actual lines. | The stated cause explains the repro's artifacts AND is not ruled out by any control run or step in the repro evidence. A cause that blames a component the control run shows working (the same input parses fine without the flag; the friendly error prints in the same build; the collect operator already synthesizes null at top level; the 26s cost appears with no pager in the loop), or that calls a piece of the repro evidence a "red herring" or "side effect" without showing why, or that names a cause no step or artifact in the package points at, fails. A cause stated as the issue states it passes when the repro evidence agrees with the issue. | required |
| one-bounded-change | The plan's scope statement (in-scope and not-in-scope lines), its approach steps, and its named files, read against the issue's described symptom and the repro's trigger. | Every planned step acts on the issue's symptom or on verifying the fix for it. The plan fails if it adds work the issue never asked for: a refactor, a library or runtime migration, a redesign or rewrite of the surrounding module, a new option or setting, a UI rework, a CI-matrix expansion, "while in the area" cleanups, or a second unrelated bug. Explicitly deferring related work with a reason ("out of scope: X, because Y") passes; a fix buried inside a campaign fails even when the core fix is right. | required |
| stranger-can-start | The plan's files or areas, its approach, and its order of work, read as a stranger with the repo cloned who may not ask the author anything. | The plan names at least one concrete file, module, function, or document to change AND states one chosen approach for it. It fails if a real decision is deferred to build time: "investigate", "profile and optimize", "poke around", "somewhere", "whichever is easier", "not sure which layer", "maybe also check", or two approaches offered with no choice made. An open question passes only when the plan picks a default and names the alternative as a fallback under a stated condition. Terse passes; a single named file with a single stated change is enough. | required |
| test-observable | The plan's test plan read against the repro evidence's steps and artifacts: which repro step or artifact is re-run, and what the plan says it will show after the fix. | The test plan names at least one observable outcome specific to this fix that a stranger could watch for: a value, a list, an exit code, a color or state change at a named step, a named test going from fail to pass, a measurement. Re-running the repro steps with a stated expected result passes. "Should feel fast", "nothing else should feel broken", "looks much better", or only "run the full test suite" with no outcome tied to the fix fails. | required |
| thread-engaged | The thread-highlights block (in live mode, the issue thread), looking for explicit maintainer or owner direction: an isolated culprit, a proposed or rejected approach, a works-as-intended note, a request for testing, a prior-art PR; read against the plan and the plan comment together. | If the thread holds explicit direction from a maintainer, owner, or named prior PR, the plan or comment follows it, or acknowledges it and says why it departs. It fails when such direction exists and the plan neither follows nor mentions it (a docs-only workaround when the owner has isolated the culprit in a named file and asked for testing of a patched binary; racing a prior-art PR without engaging it; re-proposing an approach the thread already rejected). A thread with no maintainer direction (zero comments, or only me-toos and reporter follow-ups) passes this check. | required |
| ai-disclosure | The repo-facts block's contribution-policy line (its stated AI policy) read against the plan comment. | Disclosure is required ONLY when the policy says AI use must be disclosed (words such as "must disclose", "all AI usage must be disclosed", "state the tool used"); then a comment with no disclosure naming the tool and the extent fails, because every package here is AI-assisted work. A policy that only restricts AI-generated text, asks for a human in the loop, or asks for the author's own words is satisfied by a comment that is specific to this issue and reads as the author's own account; it does not need a disclosure sentence. No AI policy, or a permissive one, imposes nothing. | required |
| risks-named | The plan's risks, unknowns, or open-question lines, and any deviation note. | At least one unknown or risk is named as such (what has not been measured, which variant could not be tested, what review may want changed), or the plan says plainly that it sees none for a one-site change. Confidence dressed over an untested claim ("definitely", "the version difference is a red herring") is noted here even though cause-grounded is what fails it. | preferred |
| conventions-followed | The repo-facts block's bug-report template asks and contribution asks (branch naming, PR template, tests required, marker removal) read against the plan and comment. | The plan does not contradict a stated convention: it does not plan a branch, commit, or PR shape the repo's stated rules forbid, and if the repo asks that a fix carry tests or remove a marker, the plan includes that. Silence about a convention passes; contradicting one is noted. | preferred |

## Verdict rule

accept if every `required` check passes. Any `required` check graded `fail` or `unclear` makes the verdict `reject` (unclear counts as fail: a plan I cannot verify from the package is a plan that is not ready to build from). `preferred` checks never change the verdict; they appear in the summary only. There is no third verdict and no partial credit: six required passes is accept, anything less is reject.
